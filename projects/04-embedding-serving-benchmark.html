벤치마크 설계, 측정, 원인 분석, 사내 리포트 작성은 본인 단독 작업이다. 임베딩 모델은 다른 팀이 개발했다.
기술
vLLM 0.19 / 0.28, SGLang 0.5.6 / 0.5.10, MEI 1.9.3, sentence-transformers, MTEB / MIEB, RTX 5090
핵심 결과
텍스트 66,810 tokens/s, 이미지 358 img/s(SGLang 대비 3.1배), MTEB Spearman 0.848 → 0.718 열화를 일으키는 무경고 결함 규명

배경

사내 2B 비전-언어 임베딩 모델(Qwen3 기반)을 서빙할 엔진을 골라야 했다. 이 모델은 last-token pooling을 쓴다. 시스템 프롬프트, chat template, assistant 헤더, EOT까지 정해진 토큰 레시피의 마지막 토큰 hidden state가 곧 임베딩이다.

접근

속도를 재기 전에 정합성 관문을 두었다. 각 엔진의 벡터가 sentence-transformers 참조 구현과 코사인 0.999 이상(이미지 0.995 이상)일 때만 측정했다. prefix cache는 모두 껐고, 서로 겹치지 않는 입력 풀을 순환시켰다. 동시성을 고정한 closed-loop 부하로 측정점마다 15초 이상 돌렸고, 같은 조건 재측정 오차는 −0.8%였다.

텍스트는 vLLM이 전 구간에서 앞섰다. SGLang은 처리량 기준 vLLM의 88–92%였고, 배치 예산을 키우면 격차가 11%에서 8%로 줄었다. 세 엔진 모두 예산 16K 근처에서 포화했다. 이미지는 320² 이하 단건에서만 MEI가 근소하게 앞섰고, 448²부터는 vLLM이 앞서며 크기가 커질수록 격차가 벌어졌다. MEI는 상주 VRAM이 vLLM의 절반이지만 처리량은 55–60%이고, 이미지는 정확도 기준 미달이라 권고하지 않았다. MEI의 39,366은 기동 가능한 최대 예산(8K) 값이다.

격차는 어디서 오는가

총 토큰 수를 맞춘 텍스트 요청과 이미지 요청의 지연 차이로 비전 경로 비용을 LM prefill에서 분리했다. 텍스트 prefill은 엔진 간 차이가 약 10%에 그쳤다. 이미지 격차는 거의 전부 비전 인코더에서 나왔고, flash attention을 쓰는 vLLM의 비전 인코더가 5–11배 빨랐다. 장문 텍스트에서 처리량이 꺾이는 이유도 같은 방식으로 확인했다. vLLM의 토큰당 지연 기울기는 256 → 2K 구간 17.8 µs에서 8K → 32K 구간 38.9 µs로 커졌고, 이는 어텐션의 초선형 비용이다. MEI는 요청을 사실상 순차 처리해서, 224² 기준 동시성을 1에서 32로 올려도 처리량이 1.12배만 늘었다(vLLM 2.80배).

HTTP 200 뒤의 계약 결함

참조 구현        [system][user: 입력][assistant 헤더][EOT] ← 이 토큰의 hidden state = 임베딩
vLLM 기본 요청   [system][user: 입력]                     ← 마지막 토큰이 다름
                 결과: HTTP 200, 경고 없음, 코사인 0.44(텍스트) / 0.40(이미지)

vLLM /v1/embeddings에 messages를 기본값으로 보내면 assistant 헤더와 EOT가 빠진다. 품질로 환산하면 MTEB STSBenchmark Spearman이 0.848에서 0.718로, MIEB BLINK top-1이 상대 31% 떨어졌다. 문서에는 chat_template_kwargs.add_generation_prompt를 지원한다고 적혀 있지만, 요청 병합 순서 때문에 top-level 기본값(False)이 이를 덮어쓴다. 한 메시지에 이미지 여러 장을 넣으면 오류 없이 벡터 하나가 나온다. SGLang은 임베딩 경로에서 chat template을 아예 적용하지 않아 클라이언트가 직접 렌더링해야 한다. 안전한 방법은 요청에 add_generation_prompt와 add_special_tokens를 top-level로 주거나, 서버에 EOT를 항상 붙이는 템플릿을 거는 것이다. 이때 코사인은 0.9998(텍스트), 0.9987(이미지)이다. 둘을 함께 쓰면 EOT가 두 번 붙어 다시 열화된다.

시행착오

이미지 크기 스윕에서 vLLM 지연이 768²의 19.9 ms에서 896²의 48.0 ms로 뛰는 "절벽"이 보였다. 엔진 특성으로 해석하려다 기동 플래그를 다시 보니 --max-num-batched-tokens 2048이 걸려 있었다. 기본 예산으로 재측정하자 1024²가 60.2 ms에서 30.9 ms로 내려갔고, 2048을 다시 걸면 절벽이 그대로 재현됐다. 모든 결함이 HTTP 200으로 끝났기 때문에, 정합성 관문이 없었다면 잘못된 벡터의 처리량을 비교하고 있었을 것이다.

배운 점

임베딩 서빙은 생성 서빙의 템플릿·토크나이즈 부품을 재사용하므로, 생성용 기본값이 pooling 계약과 어긋나기 쉽다. 엔진 비교 전에 참조 구현 대비 코사인 관문을 두고, 배포와 버전 업그레이드 때마다 다시 돌려야 한다. 이상한 곡선은 엔진보다 기동 플래그를 먼저 의심한다.
