배경

실시간 디지털 휴먼은 STT → LLM → TTS → 이미지 생성 순서로 모델을 호출하고, 그 결과를 C++ 미디어 엔진이 영상으로 송출한다. 대화 한 번마다 여러 모델을 거치기 때문에, 각 단계의 호출 방식과 노드 배치가 그대로 지연 시간과 클라우드 비용이 된다. 이 페이지는 그중 TTS 호출 구조 개선을 중심으로, 같은 기간에 진행한 비용 관련 작업을 함께 정리한다.

문제

사내 GPT-SoVITS TTS 모델이 CUDA Graph 적용 버전으로 업그레이드되면서 긴 문장 구간에서 추론 시간이 크게 짧아졌다. 그러나 엔진은 여전히 LLM 출력을 문장 단위로 잘라 문장마다 TTS 요청을 하나씩 보내고 있었다. 짧은 요청이 많으면 요청당 고정 비용이 반복되고, 긴 입력에서 빨라진 모델의 장점도 살리지 못한다. 동시에 첫 음성이 나오는 시점(TTFB)은 대화 체감 품질을 좌우하므로 늦출 수 없었다.

접근

동적 문장 배칭

엔진 측에 dynamic sentence batch request 로직을 추가했다. 문장을 하나씩 보내지 않고, 대기 중인 문장을 동적으로 묶어 하나의 요청으로 보낸다. 묶음 크기는 고정하지 않았고, 첫 음성 시점(TTFB)을 기존보다 늦추지 않는 것을 조건으로 두었다. 묶인 요청은 업그레이드된 모델이 빠르게 처리하는 긴 입력 구간에 해당한다.

수정 전   LLM 출력 → [s1] [s2] [s3] [s4] ... [s100]   → TTS 요청 100회
수정 후   LLM 출력 → [s1 ..] [.. s_k] [.. ] ...       → TTS 요청 25회  (−75%, 100문장 기준)
                      └ 대기 중인 문장을 동적으로 묶음 → CUDA Graph 모델의 긴 입력 구간 활용

비용 관련 작업

미디어 엔진과 GPU 추론 서버(Triton)를 서로 다른 노드 그룹으로 분리해, 엔진 프로세스 수와 GPU 추론 용량을 따로 맞출 수 있게 했다. 챗봇 모듈은 Gemini 2.5 Flash-Lite 기반으로 새로 개발하고 chat history와 token count 로직을 정리했다. LangChain 기반 RAG 모듈에는 .xlsx 문서 지원을 추가하고, 문서를 갱신해도 서버를 재시작하지 않도록 바꿨다. 2세대 이미지 모델을 엔진에 연동하면서 사전 준비 데이터 처리 과정을 새 모델에 맞게 고쳐 용량을 줄였다.

노드 비율 10:1에서 50:3으로의 변화는 GPU 노드 하나가 감당하는 엔진 프로세스가 10개에서 약 16.7개로 늘었다는 뜻이고, 같은 수의 프로세스를 운영할 때 필요한 GPU 노드가 40% 줄어든다. 챗봇 단가는 입력·출력 단가 합계 기준 o4-mini의 US$20.00 대비 US$0.50으로, 비율로는 95% 이상 낮다. 2세대 이미지 모델 연동에서는 사전 준비 데이터를 4 GB에서 800 MB로 줄였고, 연동 과정과 기존 Python 모델 구현과의 차이점을 문서로 정리해 팀에 남겼다.

시행착오

모델이 빨라졌다는 사실만으로는 서비스가 빨라지지 않았다. 호출하는 쪽이 문장 단위 요청 구조를 유지하는 한, 개선된 구간을 거의 쓰지 못한다. 반대로 요청을 무작정 크게 묶으면 첫 음성이 늦어진다. 그래서 요청 수 감소와 TTFB 유지를 한 쌍의 조건으로 놓고 검증했다. 챗봇 모델 교체도 단가표만으로 끝나지 않았다. 대화가 길어질수록 입력 토큰이 늘어나므로, 모델 교체와 함께 chat history와 token count 로직을 정리했다.

배운 점

모델 성능 개선은 호출 구조가 그 특성에 맞춰질 때 비로소 서비스 지표로 이어진다. 비용 작업은 단가, 요청 수, 노드 배치, 데이터 크기처럼 서로 다른 축에서 나오므로, 각 축의 기준값과 측정 조건을 먼저 고정해 두는 것이 비교를 정직하게 만든다.
