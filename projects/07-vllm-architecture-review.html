핵심 결과
요청 경로와 400 오류 지점, OpenAI 필드 → SamplingParams 매핑, KV 블록 예산 결정 과정을 코드 위치와 함께 문서화. 멀티모달 파서의 미할당 변수 오류를 회귀 테스트와 함께 로컬 수정(업스트림 미제출).

배경

팀은 vLLM V1 코드베이스를 6–8주에 걸쳐 구조 → 기능 → 성능 순서로 읽는 스터디를 운영했다. 분석 대상은 V1으로 한정했고, 세 사람이 요청 진입, 스케줄링과 KV 캐시, 실행 파이프라인을 나누어 맡았다. 본인 영역은 입력 파싱, 전처리, 오류 경로였다.

문제

서빙 장애의 상당수는 엔진 내부가 아니라 진입부에서 생긴다. chat template이 붙으면서 늘어난 토큰 수가 컨텍스트 한도를 넘거나, 요청 필드가 예상과 다른 내부 파라미터로 바뀌는 경우다. 또 같은 GPU에서도 기동 플래그에 따라 KV 캐시에 쓸 수 있는 블록 수가 크게 달라지는데, 이 계산 과정을 설명할 수 있는 사람이 팀에 없었다.

접근

모든 주장에는 파일·함수 위치와 재현 로그를 붙인다는 규칙을 두고, 질문은 이슈 하나에서 질문 → 추정 → 검증 중 → 검증 완료 상태로 관리했다. 먼저 POST /v1/chat/completions가 엔진에 등록되고 응답이 스트림으로 돌아오기까지를 따라갔다.

POST /v1/chat/completions                       (api_server → OpenAIServingChat)
  ├─ 모델 이름 확인
  ├─ messages 파싱 (멀티모달 content parser 포함)
  ├─ chat template 적용 (add_generation_prompt=True) → tokenize
  ├─ 길이 검사 ① prompt 토큰 > max_model_len            → 400
  ├─ 길이 검사 ② prompt 토큰 + max_tokens > max_model_len → 400
  ├─ 요청 필드 → SamplingParams
  ▼
AsyncLLM.generate()
  ├─ 입력 처리 → EngineCoreRequest → EngineCore 프로세스로 전달
  │                 └─ Scheduler waiting queue (Request 단위)
  └─ 출력: OutputProcessor(detokenize) → 요청별 수집기
  ▼
SSE: data: {chunk} … data: [DONE]

chat template이 role 구분용 special token과 줄바꿈을 넣기 때문에 실제 토큰 수는 본문 토큰 합보다 길고, 길이 검사와 리소스 계산은 이 최종 토큰 수를 기준으로 한다. 두 검사 모두 엔진에 들어가기 전에 400을 돌려주므로 한도 초과 요청이 스케줄러 큐를 차지하지 않는다.

기동 경로는 가중치 로드 → 메모리 프로파일링 → 컴파일·워밍업 → CUDA Graph 캡처 순서다. 프로파일링은 max_num_batched_tokens 크기의 0 텐서 배치로 최악의 활성 메모리 피크를 측정하고, gpu_memory_utilization으로 정한 예산에서 가중치와 이 피크를 뺀 나머지를 KV 블록으로 나눈다.

업스트림 논의는 KV offloading, attention, 가속기 플러그인 분야에서 11건을 다이제스트로 정리했다. 제안 동기, 메인테이너 반응, 결론, 코드 변경의 핵심 메커니즘을 같은 형식으로 남겼다.

시행착오

멀티모달 파서를 읽다가 parse_image_embeds가 else 없는 if 세 개로 되어 있어, dict·str·None이 아닌 값이 들어오면 placeholder가 할당되지 않은 채 UnboundLocalError가 나는 경로를 찾았다. 오디오 파서와 비동기 파서처럼 if/elif/else로 바꾸고 회귀 테스트를 추가했다(2개 파일, +36/−4). 처음에는 이 오류가 HTTP 500으로 이어진다고 보았지만, 이후 다른 기여자가 올린 같은 취지의 PR에서 메인테이너는 HTTP 경로는 요청 스키마 검증이 먼저 400을 돌려주고 오프라인 LLM.chat만 이 코드에 도달한다고 설명했고, 그 PR은 머지되지 않았다. 본인 수정은 업스트림에 제출하지 않았다. 또 초기 문서에는 요청을 V0의 SequenceGroup 단위로 큐잉한다고 쓴 부분이 있었는데, V1에서는 EngineCore 프로세스의 Scheduler가 Request 단위로 관리하므로 이 경로를 다시 확인해 고쳐 써야 했다.

배운 점

오류 경로의 영향은 코드 한 곳이 아니라 앞단 검증까지 포함한 전체 경로로 판단해야 한다. 기동 프로파일링 구조를 이해해 둔 것은 이후 32 GB 카드에서 KV 공간이 음수로 계산되던 문제를 해석할 때 바로 쓰였다.
