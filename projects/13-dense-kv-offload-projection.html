실물 없는 가속기의 효과를 어떻게 재나

27B dense LLM의 KV 캐시·attention 오프로드 효과를 지연 주입 측정과 256K·1M 예상 모델로 정량화 · 약 3분

요약목차이력서(국문)Resume (EN)
소속
Dnotitia · Inference Optimization 파트
기간
2026.10 (약 1주)
역할 범위
실험 설계, 장치 비용 모델과 지연 주입 방식 결정, 측정 방법 수정, 예상 모델의 가정 설정, 결과 판단과 보고 방향은 본인. 측정 스크립트·분석·보고서 생성은 AI 코딩 에이전트를 지휘해 작성했다. 2번째 장치 경로가 들어간 추론 엔진은 팀 코드다. 가속기 실물 측정은 하지 않았다.
기술
Qwen3.8-27B (dense, MTP), 정수 양자화, 지연 주입 모사, 정상 상태 벤치마크, 선형 비용 맞춤, RTX 6000 Ada 48 GB
핵심 결과
8K 문맥·추측 1개에서 받을 수 있는 동시 세션이 GPU 단독 44에서 오프로드 구성 64(측정 상한)로 증가. 256K 예상에서 카드당 상주 장문 대화는 GPU 대비 3.5배지만, 대화당 10 tok/s를 지키는 동시 처리 수는 가속기 1장에서 GPU보다 적어 속도 확보에 필요한 대역·연산을 역산해 제시. MTP 실제 수락률 77.8 / 61.1 / 49.1%(추측 1 / 2 / 3개).

배경

긴 문맥 서빙에서 GPU 메모리를 가장 많이 쓰는 것은 KV 캐시다. 사내 가속기를 2번째 장치로 붙여 KV 캐시 저장과 full attention 계산을 넘기면 GPU에는 가중치와 나머지 연산만 남는다. 경영진은 모델 기본 최대 문맥인 256K와 YaRN으로 늘린 1M에서 이 구성이 얼마나 이득인지 판단할 근거를 원했다. 문제는 가속기 실물이 아직 서빙 경로에 붙어 있지 않다는 점이었다.

문제

실물 없이 수치를 내야 했고, 그 수치는 두 가지를 구분해야 했다. 메모리에 올려 둘 수 있는 대화 수(용량)와, 대화마다 체감 속도를 지키며 동시에 처리할 수 있는 수(속도)다. 용량은 메모리 산술로 나오지만 속도는 GPU와 가속기가 한 스텝 안에서 어떻게 시간을 나눠 쓰는지에 달려 있다. 여기에 MTP(추측 디코딩)가 끼면 확인 토큰 수만큼 attention 일이 늘어 계산이 더 복잡해진다.

접근

엔진의 2번째 장치 경로에서 attention을 넘기는 지점마다, GPU가 가속기 비용 모델만큼 기다리게 했다. 비용 모델은 층마다 호출 고정비, 전송량, KV 읽기 ÷ 대역, attention 연산량 ÷ 연산 성능의 합이다. 이렇게 하면 GPU 쪽 실측 시간 위에 장치 몫을 얹은 스텝 시간을 얻는다.

① 수락률 측정    실제 문장 프롬프트로 MTP 추측 1–5개의 수락률 측정
② 정상 상태 벤치  세션 1–64 × 입력 1K·8K × MTP 끔·추측 1–3개
                  GPU 단독 / 오프로드(지연 주입) 두 구성
③ 선형 맞춤      실측 GPU 몫을 세션·문맥 길이에 대해 맞춤
④ 예상           RTX PRO 6000 + 가속기 1·2·4장 + RAM 256 GB 구성의
                  256K·1M 용량과 대화당 10·20 tok/s 동시 처리 수를 추측 개수별로 계산
⑤ 역산           카드당 상주 대화를 모두 10 tok/s로 처리하려면 필요한 대역·연산

결과

Qwen3.8-27B dense, RTX 6000 Ada 실측(①②)과 RTX PRO 6000 기준 예상(④). 예상치는 가속기 비용이 확인 토큰 수에 선형이라는 가정에 의존한다
항목값
MTP 실제 수락률 (추측 1 / 2 / 3개)77.8 / 61.1 / 49.1%
MTP 실측 가속, 1K, GPU 단독 (대화 1개 / 64개, 추측 1개)1.44× / 1.09×
8K·추측 1개 동시 세션 (GPU 단독 → 오프로드)44 → 64 (측정 상한)
256K 카드당 상주 대화 (GPU 대비)3.5×
256K 대화당 10 tok/s 동시 처리 (GPU / 가속기 1장 / 4장, 추측 1개)8 / 3 / 12
256K MTP 가속 (GPU 단독 추측 3개 / 가속기 1장 최대 / 가속기 연산 10배 가정)1.96× / 1.49× / 2.05×

오프로드는 용량 문제를 풀었다. 같은 GPU에서 받을 수 있는 세션이 늘었고, 256K에서는 카드 1장이 GPU보다 3.5배 많은 장문 대화를 올려 둘 수 있다. 하지만 속도는 다른 이야기였다. 대화당 10 tok/s를 지키는 동시 처리 수는 가속기 1장에서 GPU보다 적었다. 상주 대화를 모두 그 속도로 처리하려면 가속기 대역과 연산이 현재 가정보다 크게 높아야 해서, 필요한 사양을 역산해 보고에 함께 실었다. MTP도 가속기 구성에서 덜 빨라졌다. 확인 토큰이 늘면 attention 연산이 늘어나는데, 확인 토큰당 산술 강도가 가속기의 연산·대역 균형점보다 낮아 대역에 묶이기 때문이다.

시행착오

처음에는 CPU에서 도는 2번째 장치 커널을 쓰려 했지만, 가속기와 비용 구조가 달라 지연 주입으로 바꿨다. 64토큰 출력으로 잰 첫 측정은 세션끼리 생성 구간이 겹치지 않아 동시성을 재지 못했고, 긴 출력과 정상 상태 벤치로 교체했다. 30K 입력 측정은 출력 예산 때문에 시간이 왜곡되어 문맥과 예산을 늘려 다시 쟀다. 예상치를 8K 기준으로 썼다가 보고 기준인 256K·1M으로 다시 썼고, 숫자마다 "무엇을 세는지"(상주 대화 수인지, 속도 기준을 지키는 동시 처리 수인지)를 적도록 보고서 규칙을 고쳤다. 가속기 attention 시간을 확인 토큰 수에 선형으로 둔 것은 가정이다. 연산 배열의 패스 단위로 시간을 매기면 세부 수치가 달라질 수 있어 한계로 명시했다.

배운 점

"몇 개를 올릴 수 있나"와 "몇 개를 제 속도로 돌릴 수 있나"는 다른 질문이고, 오프로드 설계는 앞의 질문에만 답하기 쉽다. 실물이 없을 때는 장치 비용을 GPU 실측 위에 지연으로 얹는 방식이 빠르고 정직한 근사였다. 다만 예상치가 어떤 가정 위에 있는지를 숫자 옆에 같이 적어야 보고가 오해 없이 읽힌다.
