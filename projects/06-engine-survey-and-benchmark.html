Dnotitia · AI Group, Inference Optimization 파트
기간
2026.09 (조사 리포트 09.17 완료, 벤치마크 계획 09.18, smoke 측정 09.18 – 09.22)
역할 범위
6개 엔진 리포트 작성(AI 보조, 코드 인용과 결론은 본인 검증), 벤치마크 계획 설계, 두 서버에서의 smoke 측정과 문제 해결 본인 수행. 조사는 코드 리뷰이며 구현이 아님. 벤치마크 본 매트릭스는 아직 실행하지 않음.
기술
vLLM 0.23 / 0.28, SGLang, llama.cpp, MLX, CUDA Graph, roofline 분석, RTX 5090 (32 GB), RTX 6000 Ada (48 GB)
핵심 결과
공용 런처 설정이 eager 모드를 조용히 강제한 것을 발견 — 35B MoE의 vLLM TPOT 57 ms → 8.1 ms(약 7배). 27B FP8은 32 GB 카드에서 7개 기동 구성 중 1개만 동작함을 확인.

배경

팀은 NPU 이식을 염두에 두고 Qwen3.8-Flash-Next를 서빙할 엔진을 골라야 했다. 이 모델은 48개 층 중 36개가 Gated DeltaNet(GDN), 12개가 sparse attention인 하이브리드 구조이고, MoE, 가속기 밖에 두는 51B 파라미터 n-gram 임베딩, MTP 모듈을 함께 쓴다. 어느 엔진이 이 구성요소를 실제로 어떻게 구현하는지, 그리고 엔진 사이의 속도 차가 어디서 오는지를 알아야 했다.

문제

엔진 비교 자료는 대부분 서로 다른 양자화 포맷과 실행 설정을 섞어 놓은 채 tok/s 하나로 결론을 낸다. 이 경우 격차가 커널에서 오는지, 프레임워크 오버헤드에서 오는지, 읽는 바이트 수 차이에서 오는지 구분할 수 없다. 기능 지원 여부도 README와 실제 코드가 다른 경우가 많았다.

접근 ① 소스 수준 조사

vLLM, SGLang, llama.cpp, MLX 기반 엔진, 그리고 타사 추론 엔진 2종(CPU–GPU 협업형 엣지 엔진, 자체 CUDA 커널의 단일 GPU 엔진)을 같은 템플릿으로 정리했다. 용어 → 요약 → 설계 철학 → 핵심 기술 3가지 → 아키텍처 → 성능 → NPU 시사점 순서이고, 부록에서 각 엔진의 Qwen3.8-Flash-Next 구현과 커널 백엔드를 다룬다. 모든 코드 인용은 고정 커밋의 file:line으로 남기고, 용어집은 스크립트로 생성해 6개 리포트에서 정의가 어긋나지 않게 했다.

접근 ② 벤치마크 설계

타사 엔진과 vLLM을 Qwen3.6-27B(dense)와 35B-A3B(MoE)로 비교하되, 격차를 원인별로 나누는 것을 목표로 했다. 시간을 재기 전에 GSM8K 30문항과 코드 20문항으로 정답률을 맞추고, 엔진 간 차이가 5%p를 넘는 셀은 성능 수치를 싣지 않는다. 시나리오는 decode 지배(입력 128 / 출력 1024)부터 240K 장문맥, 30K 공유 prefix의 5턴 대화까지, 동시성 1–8로 잡았다.

정확도 관문 (GSM8K 30 + code 20, 차이 ≤ 5%p)
   │ 통과한 셀만
   ▼
c=1 decode → 대역폭 효율 = 달성 tok/s ÷ (HBM BW ÷ 토큰당 읽는 바이트)
   ├─ 포맷 차이(FP8 / NVFP4 / 4-bit) 제거 → 엔진 효율만 비교
   ├─ CUDA Graph on/off 차 → 런치·프레임워크 오버헤드
   ├─ prefix cache on/off (multi-turn) / MTP on/off
   └─ VRAM 분해: 가중치 / KV pool / 활성·그래프 workspace

MoE에서만 격차가 큰 이유는 층마다 라우팅, gather, grouped GEMM, scatter 같은 작은 커널이 많아 eager에서는 CPU 런치 비용이 decode 시간을 지배하기 때문이다. prefill 처리량은 두 모드가 거의 같아(12.4k vs 11.8k tok/s) 연산이 지배한다. 타사 엔진은 두 장비에서 비슷한 대역폭 효율을 보여, 장비 간 속도 차는 대부분 메모리 대역폭으로 설명되었다.

시행착오

활성 3B인 MoE가 27B dense보다 느린 값은 대역폭으로 설명되지 않았고, 원인은 공용 런처의 모델 계층에 남아 있던 VLLM_ENFORCE_EAGER=true였다. 이후 모든 축을 명령행에 명시하고 서버 로그의 non-default args를 결과에 첨부한다. 서버가 죽은 상태에서 vllm bench serve가 9개 점을 종료 코드 0으로 기록한 일도 있어 /health 가드와 완료 요청 수 검증을 추가했다. 대용량 체크포인트는 내려받기가 중간에 멈춰 Range 재개 다운로더와 SHA256 검증으로 받았고, pkill -f가 자신의 ssh 명령줄에 매치되어 세션을 끊는 문제도 겪었다. 32 GB 카드에서는 VL 체크포인트의 vision encoder 프로파일링과 torch.compile 경로의 추가 메모리 피크가 KV 공간을 잠식해 구성을 하나씩 줄여야 했다.

배운 점

엔진 비교에서 가장 큰 단일 요인은 엔진 자체가 아니라 설정 하나일 수 있다. 그래서 정확도 관문, 포맷 정규화, 명시적 플래그 기록이 측정보다 먼저 있어야 한다. 조사 리포트는 지원 여부를 README가 아니라 코드 위치로 확인할 때만 포팅 판단에 쓸 수 있었다.
