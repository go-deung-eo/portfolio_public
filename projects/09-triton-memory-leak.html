8개월 묵은 GPU 메모리 누적을 5일 만에 해결

Triton 클라이언트 소멸자의 공유 메모리 해제 누락 추적 · 약 3분

요약목차이력서(국문)Resume (EN)
소속
Klleon · Product AI 팀 (AI Engineer)
기간
2025.06.23 – 2025.06.27 (5일)
역할 범위
원인 조사, 재현 코드 작성, 수정, 문서화까지 본인 단독 수행. 엔진과 Triton 추론 서버의 운영·배포 환경은 팀이 관리.
기술
C++17, NVIDIA Triton Inference Server (client shared memory API), Kubernetes, Grafana
핵심 결과
수정 이후 GPU OOM 0건, 3일 주기 파드 재시작 로직 제거

배경

Klleon의 실시간 디지털 휴먼 엔진은 C++로 작성된 영상 생성·송출 엔진이 Triton Inference Server에 올라간 AI 모델을 호출하는 구조다. 엔진과 Triton 사이의 텐서는 네트워크 직렬화 대신 공유 메모리로 주고받는다. Triton client가 공유 메모리 영역을 만들어 서버에 등록하고, 추론 요청은 그 영역의 이름과 오프셋만 전달하는 방식이다. 등록된 영역은 클라이언트가 명시적으로 해제하기 전까지 서버 쪽에 남는다.

문제

Triton을 오래 띄워 두면 GPU 메모리(GRAM) 사용량이 시간에 따라 계속 올라가 결국 한계에 도달했다. 세션을 정상 종료(graceful shutdown)하든 비정상 종료하든, 또는 clear context를 호출하든 누적 양상은 같았다. 이 문제는 회사에서 처음 보고된 뒤 8개월 동안 해결되지 않았고, 운영에서는 약 3일 주기로 파드를 강제 재시작하는 로직으로 버티고 있었다.

접근

종료 방식과 무관하게 누적된다는 점에서, 모델 내부나 엔진의 세션 상태보다 엔진과 Triton 사이의 자원 등록·해제 경계를 먼저 의심했다. 그래서 Triton client 객체가 만들어지고 소멸할 때까지의 수명 주기를 따라가며 어떤 자원이 서버 쪽에 남는지 확인했다. 운영 환경에서는 재현에 며칠이 걸리므로, client 객체의 생성과 소멸을 짧은 주기로 반복하는 재현 코드를 따로 작성해 누적을 빠르게 관찰할 수 있게 했다.

[client 객체 생성]
  ├─ 공유 메모리 영역 생성
  ├─ Triton 서버에 영역 등록 (register)
  └─ 추론 요청: 영역 이름 + 오프셋만 전달
        │
        ▼
[client 객체 소멸]
  └─ 소멸자 실행 ── (수정 전) 등록 해제(unregister) 호출 없음
        │
        ▼
[Triton 서버]
  └─ 등록된 영역을 계속 보유 → 객체 수만큼 GRAM 누적 → OOM

(수정 후) 소멸자에서 unregister → 영역 반환 → GRAM 일정

추적 결과 client 객체의 소멸자에서 공유 메모리 등록 해제(UnregisterSharedMemory 계열 호출)가 빠져 있었다. 엔진 프로세스 쪽 핸들은 사라져도 Triton 서버는 해당 영역을 계속 등록된 상태로 들고 있었기 때문에, 엔진의 종료 경로를 어떻게 바꾸어도 서버 메모리는 줄지 않았다.

수정은 공유 메모리의 수명 주기를 명시적으로 정리하는 방향으로 했다. 소멸자에서 등록 해제를 호출하고, 생성·등록·해제·반환의 순서를 한곳에서 관리하도록 cleanup 경로를 보강했다.

결과

운영 환경 지표 (엔진을 사용하는 전체 Kubernetes 노드, Grafana 기준)
항목수정 전수정 후
GRAM 사용량 추이시간에 따라 우상향노드 전체에서 일정 수준 유지
GPU OOM장기 구동 시 반복 발생0건 (수정 이후 현재까지)
파드 재시작약 3일 주기 강제 재시작재시작 로직 제거, 무중단 운영
문제 지속 기간8개월 미해결5일 만에 해결

OOM이 발생하던 시기에는 Grafana의 노드별 GRAM 곡선이 시간에 따라 우상향했고, 수정 이후에는 엔진을 사용하는 모든 Kubernetes 노드에서 평탄하게 유지된다. 재시작이 필요 없어지면서 파드 재시작 로직도 삭제되었다. 재현 코드와 원인·해결 분석은 문서로 정리해 연구팀과 개발팀에 공유했다. 이력서의 "Shared VRAM 누수 해결로 크래시율 zero" 항목은 이 건과 같은 사건이다.

시행착오

처음에는 clear context나 graceful shutdown 같은 엔진 쪽 종료 절차를 의심하기 쉽다. 그러나 종료 방식을 바꾸어도 누적이 똑같이 계속된다는 사실이 오히려 범위를 좁히는 단서가 되었다. 또 운영 지표만 보고 원인을 좁히려 하면 한 번의 검증에 며칠이 걸린다. 누적을 빠르게 재현하는 코드를 먼저 만든 것이 5일 안에 끝낼 수 있었던 가장 큰 이유였다.

배운 점

프로세스 경계를 넘는 자원은 한쪽에서 핸들을 놓는다고 해제되지 않는다. 등록과 해제가 짝을 이루는지, 그 짝이 객체 수명 주기에 묶여 있는지를 먼저 확인해야 한다. 주기적 재시작 같은 워크어라운드는 증상을 가리므로, 가능하면 원인 규명과 함께 제거 일정을 잡는 것이 맞다.
