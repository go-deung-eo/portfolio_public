배경

팀은 Qwen3.8-Flash-Next를 서빙 엔진과 NPU로 옮기는 작업을 앞두고 있었다. 이 모델은 GDN, sparse attention, gated residual, n-gram 임베딩, MTP를 한꺼번에 도입해서, 구성요소 하나를 모르면 커널·캐시·메모리 설계를 판단할 수 없었다. 이후 같은 시기에 공개된 다른 모델들도 비슷한 구성요소를 다른 방식으로 쓰고 있어 비교가 필요했다.

문제

모델 소개 자료는 기능 목록을 나열하는 데 그쳐, 왜 그 구성요소가 필요한지와 서빙에서 무엇을 새로 요구하는지가 빠지기 쉽다. 블로그나 기억에 의존한 요약은 숫자가 틀리거나 tech report에 없는 주장을 report의 말처럼 옮기는 경우가 있었다.

접근

작성 규칙을 매뉴얼로 고정했다. 첫째, tech report 원문, config.json, HTTP Range로 읽은 safetensors 헤더, HF와 vLLM 구현만 근거로 쓴다. 둘째, 모든 구성요소를 앞 단계가 남긴 문제를 푸는 장치로 소개해 시리즈 전체가 하나의 사슬이 되게 한다. 셋째, report나 코드에 근거가 없는 문장에는 "(해석)" 또는 "추정"을 붙이고, 파라미터 수·메모리·FLOPs는 스크립트로 직접 계산한 값만 쓴다.

softmax attention: 길이 n에 O(n²)
  → GDN으로 48층 중 36층을 선형화        남는 문제: 전역 층 12개의 O(n²)
  → sparse attention으로 전역 층 희소화   남는 문제: 단일 residual에 정보가 섞임
  → gated residual (4 스트림)            남는 문제: 용량을 늘리면 FLOPs·HBM이 같이 늘어남
  → n-gram 임베딩 (곱셈 없는 조회, 가속기 밖)
  (+ MTP: decode 속도를 위한 추가 모듈)

예시: 51B 파라미터 n-gram 테이블을 가속기 밖에 두는 방식

표준 임베딩은 토큰 하나를 키로 행 하나를 읽는다. Qwen3.8-Flash-Next는 여기에 현재 토큰과 직전 1–2개 토큰을 묶은 bigram·trigram 키를 더한다. 조합 수가 너무 많아 n-gram마다 행을 줄 수 없으므로, 차수마다 해시 함수 8개(총 16개)로 고정 크기 테이블의 칸 번호를 만들고 충돌은 허용한다. 해시마다 160차원을 읽어 이어 붙이므로, 충돌이 나도 그 해시의 160차원만 다른 n-gram과 공유된다.

n-gram 임베딩 형상 (공개 config.json과 HF 구현으로 계산)
항목값계산·근거
해시 수 × 해시당 차원16 × 160bigram·trigram 각 8개, 2,560 ÷ 16

테이블을 host 메모리에 둘 수 있는 이유는 주소가 입력 토큰 id만으로 정해지기 때문이다. 토큰이 들어오는 순간 16개 행 번호를 알 수 있으므로, 가속기가 첫 층을 계산하는 동안 host가 행을 모아 보낼 수 있다. report도 이 모듈을 두 번째 층에 둔 이유를 "allowing host-memory prefetching to overlap with the computation of the first layer"라고 쓴다. MoE expert는 직전 층 활성값으로 라우팅이 정해져 미리 보낼 수 없다는 점과 대비된다.

토큰 id 도착 ─┬─ 해시 16개 → 행 번호 확정 → host gather → PCIe 전송 ─┐
              └─ 가속기: layer 1 계산 ──────────────────────────────┤
                                                      layer 2: 게이트 후 residual에 더함
프리필: 숨길 계산이 많음 (100만 토큰이면 전송 약 5.1 GB)
디코드: 숨길 구간이 토큰 1개의 layer 1뿐 → gather·DMA·동기화 고정 지연이 드러남

남는 문제는 디코드다. 전송량은 작지만 숨길 계산도 작아서 고정 지연이 그대로 드러난다(해석). 공개 HF 구현은 테이블을 장치 배치에서 빼고 CPU에서 동기로 조회하며, 비동기 prefetch는 서빙 엔진이 구현해야 할 부분으로 남아 있다.

시행착오

1차 자료끼리도 기준이 달랐다. report와 config는 층 번호를 1부터, 코드는 0부터 세어 같은 층이 Layer 2와 layers.1로 나타났고, 총 파라미터도 임베딩을 어떻게 세느냐에 따라 125B와 126B로 갈렸다. report가 n-gram 어휘 배율을 해시 하나 기준으로 셌는지 16개 합으로 셌는지도 명시되지 않아, 페이지에는 두 해석(80배, 1,280배)을 함께 적었다. 또 HF 구현은 참조용이라 일부 모듈이 마스크 기반이거나 빠져 있어, 서빙 동작은 vLLM 구현으로 따로 확인해야 했다.

배운 점

"새 구성요소가 무엇을 푸는가"보다 "무엇을 새 문제로 남기는가"를 함께 적으면 서빙 팀이 해야 할 일이 바로 드러난다. 수치를 직접 계산하는 규칙은 번거롭지만, 행 수·메모리처럼 설계 판단에 쓰이는 값에서 report의 반올림이나 기준 차이를 찾아내는 데 필요했다.
