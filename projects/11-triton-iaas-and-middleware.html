배경

Tmax Cloud는 NVIDIA Triton Inference Server를 추론 엔진으로 쓰는 모델 서빙 클라우드 플랫폼을 만들고 있었다. 외부 요청은 사내 서버 프레임워크가 받는다. 이 프레임워크는 Linux epoll 기반 이벤트 드리븐 멀티스레드 구조이고, 사내 자체 L7 통신 프로토콜을 쓴다. 입사 후 수습 기간에는 이 프레임워크를 분석하며 채팅 서버를 만들었고, 정규직 전환 후 서빙 IaaS의 추론 서버 컴포넌트를 맡았다.

문제

Triton은 보통 자체 HTTP/gRPC 서버로 쓰지만, 이 플랫폼은 요청을 사내 프레임워크와 프로토콜로 받아야 했다. 따라서 Triton을 별도 서버로 두지 않고 core C API로 직접 호출해야 했고, 이벤트 루프를 막지 않으려면 추론·헬스 체크·통계 조회를 모두 비동기로 다뤄야 했다. 또 서빙 경로의 모든 메시지가 거치는 프레임워크의 JSON 처리가 오래된 boost::property_tree 기반이어서, 성능과 유지보수 양쪽에서 최신화가 필요했다.

접근

Triton core C API 포팅

Triton core의 inference, health check, statistics report 호출을 사내 엔드포인트에 연결했다. core API는 응답을 콜백으로 돌려주므로, 콜백에서 std::promise를 채우고 호출 측은 std::future로 결과를 받도록 감쌌다. 워커 스레드는 결과가 준비될 때까지 이벤트 루프를 붙잡지 않는다. 텐서 값을 JSON 숫자 배열로 풀어 쓰는 대신 원본 바이트를 바이너리로 실어 보내는 tensor binary encoding 확장도 프레임워크에 구현했다.

JSON 라이브러리 교체

boost::property_tree는 모든 값을 문자열 노드 트리로 다루는 범용 구조라 변환 비용이 크다. 이를 compile-time reflection으로 C++ 구조체를 직접 읽고 쓰는 glaze로 교체했다. 프레임워크의 JSON 직렬화·역직렬화 기능을 이 라이브러리 기준으로 다시 작성했다.

CI 파이프라인

GitLab CI를 새로 구성했다. 로컬 빌드, 컨테이너 이미지 빌드, 기능 테스트(E2E), 배포의 4단계이며, E2E 단계에서 쓰는 Python 테스트 클라이언트를 직접 작성했다.

수습 과제: 채팅 서버와 교육 자료

수습 기간에는 사내 프로토콜 기반 실시간 채팅 서버와 CLI 클라이언트를 1인으로 개발했다. 과제 범위 밖으로 IRC 프로토콜을 참고해 강퇴(KICK)와 채팅방 주제 설정(TOPIC)을 추가했고, message·topic·kick 서비스가 broadcasting 서비스를 연쇄 호출하도록 구성해 코드 재사용을 늘렸다. non-blocking accept도 조사해 발표했다. accept 이벤트 한 번에 여러 클라이언트 연결을 받을 수 있다는 점을 분석하고, Linux kernel의 socket 대기 큐 구조를 바탕으로 DDoS 공격 가능성과 예방책을 정리했다. 본인의 수습 발표 자료를 바탕으로 수습 팀원 교육 자료의 디자인과 구성도 도표 중심으로 전면 개선했다.

시행착오

non-blocking 소켓에서는 준비 이벤트 하나가 연결 하나를 뜻하지 않는다. 대기 큐에 쌓인 연결을 한 번에 하나씩만 꺼내면 연결이 큐에 남고, 반대로 무제한으로 꺼내면 공격 트래픽에 이벤트 루프가 묶일 수 있다. 이 양면은 API 문서만으로는 보이지 않고, 커널의 socket 대기 큐 동작까지 내려가서야 설명이 되었다. glaze는 구조체 정의를 기준으로 동작하므로, property_tree처럼 경로 문자열로 값을 꺼내던 코드는 그대로 옮길 수 없고 메시지마다 구조체 매핑을 명시해야 한다. 라이브러리 교체는 곧 메시지 형식을 코드로 고정하는 작업이기도 했다.

배운 점

콜백 기반 C API를 이벤트 루프 프레임워크에 붙일 때는, 결과를 기다리는 위치를 어디에 둘지가 설계의 핵심이다. 라이브러리 교체 같은 기반 작업은 서빙 경로 전체에 누적 효과를 내므로, 측정 가능한 단위로 쪼개 전후를 비교해 두는 편이 설득력이 있다.
